# 05 教師用弱點答案對照表

本文件專供教師上課教學、課堂演示與批改作業使用，詳細記錄了靶場中每個弱點的成因、驗證 Payload、ZAP 掃描反應、安全修補檔案以及課堂講解核心要點。

---

## 🛠️ 各弱點教學演示指引

### 1. 課程搜尋 SQL 注入 (SQLi)
- **弱點位置**：`/courses.php` 與 `/course_detail.php`
- **檢測方式**：
  - ZAP 主動掃描：會發出 `SQL Injection` 警報 (🔴 High Risk)。
  - 手動驗證：在查詢框輸入 `'`，系統爆出資料庫詳細報錯資訊。
  - 滲透 Payload (在詳細頁 ID 後方串接)：
    `course_detail.php?id=1 UNION SELECT 1,username,password_hash,role,name,email,7 FROM users`
    *(此時網頁會印出所有人的 MD5 密碼雜湊，可用於進一步破解)*。
- **修補版檔案**：`app-fixed/public/courses.php` 與 `course_detail.php`
- **上課講解重點**：
  - 說明拼接 SQL 語句 `$sql = "SELECT ... WHERE id = " . $id` 的危害。
  - 講解 PDO 參數化查詢 (Prepared Statements) 如何透過預編譯，將使用者輸入視為純資料而非 SQL 指令執行。

---

### 2. 校園留言板 Stored XSS
- **弱點位置**：`/messages.php`
- **檢測方式**：
  - ZAP 主動掃描：會發出 `Cross Site Scripting (Stored)` 警報 (🟡 Medium Risk)。
  - 手動驗證：在留言內容中填入：
    `<script>alert(document.cookie)</script>`
    送出後，每次訪問該頁面都會彈出 Cookie，證明 Session ID 可被竊取。
- **修補版檔案**：`app-fixed/public/messages.php`
- **上課講解重點**：
  - 示範 Stored XSS 能在無感的情況下，將惡意 JS 存在資料庫中傳播給所有訪問者。
  - 說明 `htmlspecialchars($str, ENT_QUOTES, 'UTF-8')` 如何將特殊字元 (如 `<` 改成 `&lt;`) 進行 HTML 編碼以阻斷程式碼執行。

---

### 3. 個人資料水平越權 (IDOR)
- **弱點位置**：`/profile.php?id=X` 及 `/api/profile.php?id=X`
- **檢測方式**：
  - ZAP 主動掃描：自動化工具通常**無法**偵測此漏洞，因為此頁面有 200 OK 正常回應。
  - 手動驗證：以 `student01` (ID=2) 登入，修改 URL 參數為 `id=3` (student02)，發現能檢視李小美的個資並直接進行修改。
- **修補版檔案**：`app-fixed/public/profile.php`
- **上課講解重點**：
  - 解釋何謂 Insecure Direct Object Reference。
  - 說明「登入驗證」不等於「授權驗證」。每次收到對特定物件 ID 的請求時，後端必須查詢該物件的擁有者，確認其是否與 Session 中的登入者 ID 一致。

---

### 4. 隱藏欄位參數竄改 (Mass Assignment)
- **弱點位置**：`/profile.php` (修改個人資料)
- **檢測方式**：
  - 手動驗證：
    1. 以 `student01` 登入，進入 `profile.php`。
    2. 按下 F12 檢視原始碼，發現隱藏欄位 `<input type="hidden" name="role" value="student">`。
    3. 將 `value` 修改為 `admin`，送出修改。
    4. 登出再重新登入，會發現右上方的角色已變為 `admin`，且能進入管理後台。
- **修補版檔案**：`app-fixed/public/profile.php`
- **上課講解重點**：
  - 講解 Mass Assignment 的成因：後端直接將前端傳遞的陣列（或參數）對應欄位更新至 SQL，未做白名單過濾。
  - 修補重點：後端更新時應明確列出要修改的欄位（如姓名、電話），完全不接受來自前端的 `role` 傳值。

---

### 5. 檔案下載路徑遍歷 (Path Traversal)
- **弱點位置**：`/download.php?file=X`
- **檢測方式**：
  - ZAP 主動掃描：會發出 `Path Traversal` 警報 (🔴 High Risk)。
  - 手動驗證：將 `file` 參數修改為 `../src/db.php`，送出後成功下載資料庫連線程式，取得資料庫密碼 `rootpassword`。
- **修補版檔案**：`app-fixed/public/download.php`
- **上課講解重點**：
  - 說明攻擊者如何利用 `../` 脫離 Web 根目錄，存取主機系統底層檔案（如 `/etc/passwd`）。
  - 修補重點：介紹「查表法」，前端僅傳遞隨機 ID（如 `file_id=1`），後端向資料庫查表取得真正的實體路徑，使攻擊者完全失去對檔案路徑的控制權。

---

### 6. 活動報名金額負數 (商業邏輯缺陷)
- **弱點位置**：`/event_register.php` (數量與單價參數)
- **檢測方式**：
  - 手動驗證：
    1. 進入活動報名頁面，開啟 ZAP Breakpoint。
    2. 點選送出報名，在 ZAP 中攔截 POST 請求。
    3. 將數量參數 `quantity` 改成 `-2`，放行。
    4. 報名成功，我的報名明細中，實付金額變為負數！且活動的賸餘名額反而增加了 2 名。
- **修補版檔案**：`app-fixed/public/event_register.php`
- **上課講解重點**：
  - 說明商業邏輯漏洞自動化工具難以掃描的原因，需手動分析業務邏輯。
  - 修補重點：後端在接收數值時必須進行完整性與範圍校驗（如 `quantity` 必須大於 0 的正整數）。

---

### 7. 後台命令注入 (Command Injection)
- **弱點位置**：`/admin/ping.php`
- **檢測方式**：
  - ZAP 主動掃描：會發出 `Remote Code Execution (RCE)` 警報 (🔴 High Risk)。
  - 手動驗證：在 Ping 測試框輸入 `127.0.0.1; whoami`，結果會輸出 `www-data`，代表成功執行系統命令。
- **修補版檔案**：`app-fixed/public/admin/ping.php`
- **上課講解重點**：
  - 說明 `shell_exec()` 拼接使用者參數的危害。
  - 介紹過濾輸入（僅限 IP 格式）與使用 `escapeshellarg()` 跳脫引數參數的安全寫法。

---

### 8. 任意檔案上傳 Webshell
- **弱點位置**：`/upload.php`
- **檢測方式**：
  - 手動驗證：
    1. 寫一個簡單的 `backdoor.php` 檔案，內容為 `<?php system($_GET['cmd']); ?>`。
    2. 在大頭貼上傳頁面上傳此檔案。
    3. 點選上傳成功的網址連結，在 URL 後方加入 `?cmd=cat /etc/passwd`，即可在網頁上執行命令。
- **修補版檔案**：`app-fixed/public/upload.php`
- **上課講解重點**：
  - 說明檔案上傳的三層防禦：
    1. 副檔名檢查 (Whitelist)。
    2. MIME 類型檢驗（利用 `finfo` 讀取檔案特徵）。
    3. 上傳目錄的解析控制（透過 `.htaccess` 禁用 PHP 執行）。

---

### 9. 忘記密碼 Token 繞過
- **弱點位置**：`/reset_password.php`
- **檢測方式**：
  - 手動驗證：進入重設密碼頁面（步驟2），使用 ZAP 攔截 POST 請求。將 hidden 參數 `username` 從當前帳號修改為 `admin`，放行。發現成功修改了 `admin` 的密碼，且完全不需要知道 admin 的 Token。
- **修補版檔案**：`app-fixed/public/reset_password.php`
- **上課講解重點**：
  - 說明此類「流程控制缺陷」的邏輯。後端雖產生並要求 Token，但在寫入密碼前「忘記」去資料庫中對比該 Token 是否屬於該 `username`。
  - 講解防重放（一次性使用）與時效性設計。

---

### 10. 缺失日誌紀錄 (不完整的日誌記錄 - Logging Failures)
- **弱點位置**：`/admin/logs.php`
- **檢測方式**：
  - 手動驗證：
    1. 在弱點版故意嘗試多次登入失敗（模擬暴力破解攻擊），或進入後台下載敏感學生名冊。
    2. 隨後以 `admin/admin` 成功登入，進入後台日誌頁面。
    3. **預期結果**：日誌中僅會顯示您剛才「登入成功」的紀錄，而之前的「多次登入失敗」與「匯出名冊」等關鍵安全事件卻完全沒有被記錄下來，展現了「選擇性記錄/不完全日誌」的盲區缺陷。
- **修補版檔案**：`app-fixed/src/helpers.php` (中的 `write_audit_log` 完整實作)
- **上課講解重點**：
  - 說明安全日誌與監控在資安事件調查與入侵鑑識 (Forensics) 中的關鍵作用。
  - 指導學生理解：合格的日誌策略不應只記錄「正常交易」（如登入/登出），更必須完整涵蓋「異常與安全敏感事件」（如登入失敗、權限變更、大範圍個資讀取與越權存取嘗試）。

---

### 11. 補充演練 - 網址轉向漏洞 (Open Redirect)
- **弱點位置**：`/redirect.php?url=X` 或是 `/login.php?redirect=X`
- **檢測方式**：
  - ZAP 主動掃描：會發出 `Open Redirect` 警報 (🟡 Medium Risk)。
  - 手動驗證：存取 `http://localhost:8080/redirect.php?url=https://www.google.com`，系統將毫無攔截地在 2 秒後直接將瀏覽器跳轉至外部的 Google 首頁。
- **修補版檔案**：`app-fixed/public/redirect.php`
- **上課講解重點**：
  - 說明攻擊者如何結合 Open Redirect 與釣魚郵件 (Phishing) 進行社交工程攻擊。使用者往往只確認網址開頭是官方網站（例如 `http://school.edu.tw/redirect.php?url=...`），便放心地輸入帳密登入，卻被後續悄悄轉導至惡意的冒牌網站。
  - 介紹「跳轉白名單」的安全防護機制，說明後端如何解析並比對目標主機 (Host)，只允許相對路徑與內部信任的網域。
